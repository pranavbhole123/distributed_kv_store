
Relevant question for this phase: why does advanceCommitIndexLocked only directly commit a quorum-replicated entry when that entry is from the leader’s current term, even if an older-term entry also has a majority?

Your intuition is right. Small correction: it is “not from the current **term**,” not current index.

Raft cannot mark an older-term entry committed merely because it sees that entry on a majority. A later candidate can have a log with a newer last term, win votes, and overwrite that apparently-majority older entry.

Example with five nodes:

```text
Term 2:
S1 is leader.
It writes A at index 2, term 2.
A reaches S1 and S2 only. Not committed.
```

```text
Term 3:
S1 is unavailable.
S5 becomes leader and writes a conflicting B at index 2, term 3
to some other nodes.
```

Later, S1 may return and become leader in term 4. It might replicate its old entry `A` to S3:

```text
S1, S2, S3: index 2 = A, term 2
S4, S5:     index 2 = B, term 3
```

Now `A` exists on 3/5 nodes: a majority.

But Raft still must not call `A` committed.

Why? In term 5, S5 can run for leader. Its last entry has term 3, while S1/S2/S3 end with term 2. Raft’s “up-to-date log” voting rule considers S5’s term-3 log newer, so it can win votes and then overwrite `A` with `B`.

So if S1 had told a client “A is committed,” that client’s acknowledged write could later disappear. That is the safety violation the current-term rule prevents.

What makes it safe is this:

```text
Term 4 leader S1:
index 2: A, term 2
index 3: C, term 4   <- replicated to a majority
```

When `C`—an entry from S1’s current term—reaches a majority, S1 can commit index 3. This also commits every earlier entry, including `A`.

Any future leader that can win must contain the committed current-term entry `C` at index 3. Because Raft logs match by prefix, that future leader must also contain `A` at index 2. Now `A` cannot be overwritten.

So the exact rule is:

```text
Directly commit only a quorum-replicated entry from the current term.

Once that happens, all earlier entries become committed indirectly.
```

That is why the code checks:

```go
if r.log[index-1].Term != r.currentTerm {
    continue
}
```
