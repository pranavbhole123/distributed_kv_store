You found the important distinction: we did **not** give the client a definitive “no, this write will never happen.”

We gave it:

```text
503 / timeout / not confirmed by a majority
```

That means:

```text
the client does not know the outcome
```

The old leader may have appended the entry locally before it lost quorum. A later leader may inherit and commit it. That is allowed.

So if the old client sees:

```text
503 Service Unavailable
```

it must interpret it as:

```text
“my write may or may not have committed; retry carefully.”
```

Not:

```text
“my write was rejected and definitely will not appear.”
```

The highlighted step means a follower only ACKs the no-op after it has the leader’s entire preceding prefix—either it already had those entries, or it accepted them in that same `AppendEntries`. Thus, a quorum ACK for the no-op proves that quorum holds the whole prefix. Annotation 1

And yes: without a no-op, the **first successful client write of the new leader does exactly the same thing**.

```text
new leader inherits old entries
→ client sends a new SET
→ leader appends current-term SET
→ majority replicates it
→ current-term SET commits
→ all preceding inherited entries commit too
```

The no-op is simply a fake empty “first write” made by the leader itself.

Why need it?

```text
old leader successfully committed SET a=1
→ old leader replied success to client
→ old leader dies before followers receive LeaderCommit
→ new leader has SET a=1 in its log, but has commitIndex=0
→ no clients send any new write
```

Without a no-op, the new leader has no current-term entry to commit. So `SET a=1` can remain unapplied forever, even though the old client was already told success.

With the no-op:

```text
new leader appends NOOP in its term
→ replicates it to majority
→ NOOP commits
→ SET a=1 beneath it commits and is applied
```

For an old entry that was never committed, it can also become committed later if the new leader replicates that prefix plus its no-op to a majority. That is valid: the original client got only an uncertain failure, not a guaranteed rejection.


Yes—this is intentional Raft behavior.

Small correction: we replied “not confirmed” to the **client**, not a follower.

If the old leader already appended the command, the command can later be included in a new leader’s prefix and reach a majority. Then it may commit.

That is safe because the client never received a definite rejection—only an uncertain outcome:

```text
not committed yet / timeout / retryable failure
```

So Raft preserves safety, but the client needs request IDs for future non-idempotent operations to handle that ambiguity cleanly.
